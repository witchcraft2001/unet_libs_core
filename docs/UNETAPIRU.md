# UNET - универсальный сетевой DLL API

UNET - это сетевой интерфейс, не зависящий от бекенда и поставляемый в виде
DLL формата libman 1.3 / L1. Один контракт, два взаимозаменяемых бекенда:

- **UNETESP.DLL** - Sprinter-WiFi (ESP8266 с прошивкой ESP-AT). Поставляется
  и реализован в этом пакете. **Прошивка: только ESP-AT 2.2.2.** DLL собрана
  под набор команд 2.2.2 с полным путём приёма по trigger-4; отката к 2.2.1 в
  ней нет. `NETINIT` возвращает `NERR_NONET`, если активная сессия NETUP не
  соответствует `NET_ESP_FW=2.2.2`, а имя в её заголовке L1 читается как
  `UNET ESP 2.2.2` (показывается утилитой UNETTEST). Сначала нужно запустить
  NETUP с прошивкой 2.2.2.
- **UNETRTL.DLL** - Ethernet-карта RTL8019A. Те же номера функций и коды
  ошибок; реализована отдельно в проекте sprinter-rtl8019a (см. приложение по
  RTL ниже).

Бекенды различаются только тем, что они объявляют через `GETCAPS`, но никогда
нумерацией функций. Оба текущих бекенда объявляют `CAP_MULTICHAN` (два
одновременных соединения): UNETESP начиная с 0.3, UNETRTL начиная с 0.2.5x.
Всегда следует проверять `GETCAPS` во время выполнения, а не исходить из
фиксированного набора для каждого бекенда - это переносимое правило, вокруг
которого построен весь этот API.

Потребитель, написанный на asm, C или Pascal, загружает бекенд через libman
(`l_load` / `l_call` / `l_free`) и управляет TCP, UDP, разрешением имён и ping
через нумерованные функции. Поскольку ABI одинаков у всех бекендов, один
двоичный файл потребителя может работать с любой картой - имя DLL выбирается
во время выполнения (например, из переменной окружения `NET`: `UNET` + тег
бекенда).

Формальный машиночитаемый контракт генерируется из
[abi/unet_abi.toml](../abi/unet_abi.toml) - см.
[bindings/asm/unet.inc](../bindings/asm/unet.inc) (рядом, в `bindings/`,
лежат версии для Solid C и Pascal). Этот документ - справочник в текстовом
виде, он описывает сценарии использования, которые заголовок передать не может.

## Загрузка и соглашение о вызовах

libman - это модуль на стороне потребителя (`l_load` / `l_call` / `l_free`), а
не резидентный сервис. Потребитель встраивает его (asm: `libman13.asm`;
Pascal: `LIBMAN.INC`) и вызывает:

```
    ld   hl,filename      ; "UNETESP.DLL",0
    ld   a,window         ; 1 (0x4000) or 2 (0x8000) - NEVER 3
    call l_load           ; -> HL = handle, CF=1 on error
    ...
    ld   hl,(handle)
    ld   b,function       ; UNET_FN_*
    call l_call
    ...
    ld   hl,(handle)
    call l_free
```

**Разрешение имени DLL.** `l_load` открывает файл через файловый API DSS,
который разрешает имя только относительно **текущего каталога** - он не ищет
ни в `PATH`, ни в собственном каталоге программы-потребителя. Поэтому
потребитель, запущенный через `PATH` из постороннего каталога, не найдёт DLL,
лежащую рядом со своим EXE. Есть два надёжных способа:

- Сначала найти DLL рядом со своим EXE: вызвать DSS `APPINFO`
  (`B = APPINFO_EXE_HOMEDIR`, `C = DSS_APPINFO`), чтобы получить каталог
  своего EXE, дописать имя DLL и передать этот полный путь в `l_load`; если
  `APPINFO` недоступен - откатиться на голое имя. `UNETTEST` делает именно так
  (`RESOLVE_DLL_PATH` в `src/apps/unettest.asm`, по образцу поиска NET.CFG в
  `NETUP`).
- Либо просто запускать потребителя из каталога, где лежит DLL, либо
  передавать полный путь.

**Диагностика сбоев (расширение вендорной копии libman).** После того как
`l_load` вернул `CF=1`, копия libman из Sprinter-ESP-Kit публикует два байта,
чтобы потребитель мог сообщить, *почему* загрузка не удалась (в стандартном
libman 1.3 их нет, и они действительны только если `l_load` вернул ошибку):

- `LIBMAN.l_reason` - стадия, на которой произошёл сбой: `LR_MEMORY`,
  `LR_OPEN`, `LR_IO`, `LR_FORMAT`, `LR_INIT`, `LR_LIMIT`, `LR_CALL`.
- `LIBMAN.l_dsserr` - исходный код ошибки DSS на этой стадии (например,
  3 = файл не найден, 4 = путь не найден, 30 = нет свободной памяти) либо код
  отказа функции INIT самой DLL для `LR_INIT`. `LR_CALL` отличает
  некорректную внутреннюю таблицу/окно от сбоя DSS `SETWIN`, вместо того чтобы
  выдавать и то и другое за отказ INIT.

Вендорный диспетчер намеренно направляет вызовы через явные функции DSS
`SETWIN1`/`SETWIN2`/`SETWIN3`, а не через обобщённую `SETWIN` (`0x38`).
Текущая Estex-DSS вычисляет порт слота для обобщённой функции с `0x42` там,
где нужно `0x82`, и из-за этого может сообщить об успехе, так и не отобразив
DLL в запрошенное окно. Явные функции используют правильные
константы `SLOT1`/`SLOT2`/`SLOT3` и работают как на старых, так и на текущих
реализациях DSS.

Дисциплина регистров для всех функций UNET:

- Аргументы передаются **только в A, DE, IX, IY**. HL и BC расходуются
  диспетчером libman. Вендорный диспетчер сохраняет IX/IY вокруг своего
  внутреннего вызова DSS `SETWINn`; стандартный libman 1.3 этого не делает,
  хотя DSS/BIOS имеет право портить индексные регистры.
- Результаты возвращаются в **A, DE, IX, IY**.
- **Каждая функция возвращает свой статус в A** (0 = `NERR_OK`, иначе код
  `NERR_*`). Диспетчер **не** передаёт наружу флаг переноса пользовательской
  функции, поэтому проверять нужно A, а не CF.
- Библиотека не реентерабельна; выполнять следует по одному вызову за раз.

### Правила по окнам и буферам (важно)

- Загружать DLL следует **только в окно 1 (0x4000) или окно 2 (0x8000).**
  Никогда в окно 3 (0xC000): бекенд ESP отображает туда свой ISA UART при
  каждом вызове и выгрузил бы собственный код. Хук загрузки DLL распознаёт
  окно 3 и отказывается загружаться (`l_load` завершается ошибкой). (Старый
  `loaddll` из Solid-C жёстко зашит на окно 3 и поэтому несовместим.)
- Все буферы вызывающего (строки хоста/порта, полезная нагрузка send/recv,
  приёмники для GETINFO/LASTERR) должны находиться **ниже 0xC000 и вне того
  16-килобайтного окна, в которое загружена DLL** - буфер целиком, а не только
  его первый байт: проверяются оба конца диапазона (`buf .. buf+len-1` либо
  завершающий ноль строки). Нарушения возвращают `NERR_PARAM`.
- Указатели в **окно 0 (`0x0000..0x3FFF`) принимаются**. DLL не проверяет,
  какая страница туда отображена. Если программа заменяет системную страницу
  DSS своей собственной, то сохранение и безопасное восстановление этого
  отображения полностью на ответственности вызывающего.
- Строки хоста ограничены **128 байтами**, а строки порта - **15 байтами**
  (более длинные аргументы возвращают `NERR_PARAM`); это защищает буферы
  фиксированного размера, в которых DLL собирает AT-команды.
- Следует держать не менее ~256 байт свободного стека на время вызова.
  Загрузчик libman и путь приёма ESP используют стек вызывающего.
- Какое окно выбрать:
  - Потребитель, чей собственный код расположен по 0x8100 (окно 2 -
    большинство C-программ на SDCC и лёгкие утилиты DSS), загружает DLL в
    **окно 1**.
  - Потребитель, чей код расположен по 0x4100 (окно 1 - Turbo Pascal,
    собранный с `/D:8000`), загружает DLL в **окно 2**.

## Справочник функций

| # | Функция | Вход | Выход |
|---|------|----|-----|
| 0 | INIT | - | (хук загрузки libman; проверяет окно) |
| 1 | FINI | - | (хук освобождения libman; закрывает соединение) |
| 2 | GETCAPS | - | A=0, DE=возможности, IX=версия ABI |
| 3 | NETINIT | - | A |
| 4 | NETDONE | - | A=0 |
| 5 | CONNECT | A=chan, DE=host, IX=port | A |
| 6 | SEND | A=chan, DE=buf, IX=len | A, DE=отправлено |
| 7 | RECV | A=chan, DE=buf, IX=max, IY=timeout_ms | A, DE=получено, IX=флаги |
| 8 | CLOSE | A=chan | A |
| 9 | STATUS | A=chan (или 0xFF) | A, DE=состояние |
| 10 | UDPOPEN | A=chan, DE=host, IX=rport, IY=lport\|0 | A |
| 11 | RESOLVE | DE=host, IX=dest(>=16) | A, dest="a.b.c.d" |
| 12 | PING | DE=host, IY=timeout_ms | A, DE=время обхода, мс |
| 13 | RXPAUSE | - | A |
| 14 | RXRESUME | - | A |
| 15 | GETINFO | A=поле, DE=dest, IX=max | A |
| 16 | LASTERR | DE=dest, IX=max | A=0 |
| 17 | SETOPT | A=опция, DE=значение | A |
| 18-23 | (зарезервировано) | - | A=NERR_NOTSUP |

`host` и `port` - ASCII-строки, завершённые NUL (например, `"example.com",0` и
`"80",0`).

Байт канала выбирает одно из двух независимых соединений. Бекенд, сообщающий
`CAP_MULTICHAN`, принимает канал 0 и канал 1 и может держать оба открытыми
одновременно; бекенд без этого бита принимает только канал 0. Любое другое
значение возвращает `NERR_PARAM`. Ориентироваться всегда нужно на бит
возможностей, а не на имя бекенда: сейчас его сообщают оба (UNETESP начиная с
0.3, UNETRTL начиная с 0.2.5x), но у более старого или будущего бекенда двух
каналов может не быть. См. "[Два канала](#два-канала)" ниже.

`NETINIT` должен быть вызван (и успешно завершён) до `CONNECT`, `UDPOPEN`,
`RESOLVE` или `PING`; иначе они вернут `NERR_STATE`.

### Функции 0 / 1 - INIT / FINI

libman вызывает их при загрузке и освобождении. Напрямую вызывать их не надо.
INIT проверяет, что DLL не загружена в окно 3; FINI закрывает всё ещё открытое
соединение.

### Функция 2 - GETCAPS

Возвращает битовую маску возможностей в DE и версию ABI (`major<<8|minor`) в
IX. Может вызываться до `NETINIT`. Прежде чем полагаться на нумерованные
функции, следует проверить старший байт версии ABI. UNETESP 0.4 сообщает
`0x031F` = `TCP | UDP | RESOLVE | PING | RXFLOW | MULTICHAN | ASYNCSEND`
(0.3 сообщала `0x011F`, 0.2 - `0x010F`). Версия ABI остаётся `0x0100`: два
канала и приостанавливаемые отправки обнаруживаются через биты возможностей, а
не через смену версии.

### Функция 3 - NETINIT

Инициализирует канальный уровень: проверяет, что сеть настроена (см.
"Поднятие сети" ниже), находит и инициализирует UART на заданной скорости,
опрашивает ESP (один раз сбрасывая его, если тот молчит), включает управление
потоком RTS/CTS с обеих сторон, закрывает оставшийся от прошлой работы сокет и
включает режим множественных соединений (`AT+CIPMUX=1`). Сокет обязательно
закрывается до смены режима: пока соединение открыто, ESP-AT команду
`AT+CIPMUX` отклоняет. А раз соединение при этом действительно закрывается,
NETINIT заодно сбрасывает состояние обоих каналов - поэтому повторный
`NETINIT` с последующим `CONNECT` безопасен.

После смены режима NETINIT отправляет `AT+CIPTCPOPT=5,-1,0,4000` (по
возможности: `ERROR` допускается). Это ограничивает внутреннюю TCP-отправку
прошивки значением `SO_SNDTIMEO` в 4 с. Без этого - по умолчанию в прошивке
таймаута *нет* - ESP-AT v2.2.2 удерживает мьютекс сокета на всё время
блокирующего `lwip_send`, а поскольку для печати `+IPD` нужен тот же мьютекс,
одна отправка, застрявшая на ретрансмиссиях Wi-Fi, полностью заглушает вывод
UART модуля - и приглашения, и `SEND OK`, и входящий поток - до завершения
отправки; проверено на ядре `v2.2.2.0_esp8266` (`at_sending_data` /
`at_process_recv_socket` / `s_at_socket_mutex`). С установленной опцией
застрявшая отправка завершается собственным `SEND FAIL` модуля в течение 4 с -
раньше 5-секундного клиентского таймаута DLL - и поток возобновляется.
Возвращает `NERR_OK`, `NERR_NONET` (не сконфигурировано), `NERR_HW` (нет
карты / нет ответа) или `NERR_BUSY` (IP-стек ESP ещё разогревается после
подключения).

### Функции 4 / 8 - NETDONE / CLOSE

`CLOSE` закрывает **один** канал и идемпотентна. Данные, ещё буферизованные
для этого канала, отбрасываются: для корректного завершения нужно сначала
читать до `NERR_CLOSED`.

`NETDONE` закрывает все каналы и возвращает ESP в режим одиночного соединения
(`AT+CIPMUX=0`), который и ожидают увидеть штатные утилиты (WGET, FTP, TELNET,
...). Сама сеть остаётся поднятой, поэтому последующий `CONNECT` всё равно
работает - он сам заново включает режим множественных соединений.

### Функция 5 - CONNECT

Открывает TCP-соединение с `host:port` на заданном канале. Внутри повторяет
попытки, пока ESP сообщает `busy` (его IP-стек может ещё разогреваться сразу
после `NETUP`). `NERR_STATE`, если этот канал уже открыт (состояние другого
канала значения не имеет), `NERR_DNS`, если имя не удалось разрешить силами
ESP, `NERR_CANCEL`, если пользователь отменил незавершённое соединение (при
включённых `CANCELKEYS`), `NERR_CONNECT` при любом другом сбое.

Открытие канала очищает всё, что было для него буферизовано, поэтому новое
соединение никогда не воспроизводит данные предыдущего. Другой канал остаётся
нетронутым.

Ответ на `CIPSTART` разбирается тем же читателем двоичных данных, что и в
SEND, - он умеет отличать данные соединений от текста команд. Признаком
успеха считается само `<id>,CONNECT`; следующего за ним `OK` библиотека не
ждёт, потому что узел, сразу начавший передачу, может непрерывным потоком
`+IPD` оттеснить этот хвост команды. Любой `+IPD`, пришедший до `CONNECT`,
откладывается для нового канала, а данные после него остаются в UART и
достаются первому же RECV - как текст команды они не воспринимаются.
Запоздавшее одиночное `OK` или уведомление `CONNECT` о другом соединении
открытие не завершают. Сразу после подошедшего `CONNECT` библиотека снимает
RTS и поднимает его обратно при первом RECV или SEND: так уже накопленные в
FIFO байты переживают возврат управления через libman в приложение, а
мгновенное приветствие узла не переполняет 16550.

### Функция 6 - SEND

Отправляет `len` байт. На TCP-канале полезная нагрузка внутренне разбивается
на куски по 2048 байт (максимум для `CIPSEND` в ESP-AT), поэтому вызывающий
передаёт весь буфер одним вызовом. На UDP-канале каждый SEND - это **одна
дейтаграмма**; длины свыше 1472 (предел полезной нагрузки UDP в ESP-AT)
возвращают `NERR_PARAM`. DE возвращает число реально отправленных байт, в том
числе при `NERR_SEND`/`NERR_CANCEL`.

Замечание: данные, пришедшие от узла **во время** выполнения SEND, бекенд ESP
может потерять (см. сценарий интерактивного обмена ниже). Если узел способен
передать что-то, о чём его не просили, перед отправкой стоит вычитать всё
накопленное вызовом RECV.

### Функция 7 - RECV

Читает до `max` байт из одного канала с таймаутом в миллисекундах, заданным в
`IY`. `IY=0` означает «забрать то, что уже пришло, и сразу вернуться»:
бекенд ESP всё же делает короткую проверку UART, ограниченную одной
миллисекундой. Нулевое значение не считается «максимальным таймаутом»
(65535 мс, то есть больше минуты) - ждать так долго RECV не будет.
Возвращает:

- `A=NERR_OK, DE>0` - данные получены.
- `A=NERR_OK, DE=0` - для этого канала пока ничего нет. Обычно это истёкший
  таймаут, но при двух каналах может также означать, что бекенд отложил блок
  данных для *другого* канала и сразу вернул управление (бит 3 флагов, см.
  ниже), чтобы вызывающий не ждал, пока догрузится поток занятого канала.
- `A=NERR_CLOSED` - узел закрыл соединение. **Сначала отдаются все уже
  накопленные байты (DE>0, A=NERR_OK), и лишь *следующий* вызов возвращает
  NERR_CLOSED с DE=0**, поэтому при «FIN вместе с последним сегментом данных»
  хвост не теряется. Закрытие одного канала на другой не влияет.

В IX возвращаются флаги состояния; все они относятся только к тому каналу,
который был только что прочитан:

| бит | значение |
|-----|---------|
| 0 | слишком большая дейтаграмма была усечена (UNETESP этот бит не выставляет никогда: вместо усечения он отдаёт хвост следующим вызовом, выставив бит 1) |
| 1 | для этого канала уже накоплены ещё данные - нужно вызвать RECV снова |
| 2 | с момента последнего RECV на этом канале данные были потеряны: переполнение UART (16550 LSR) либо кадр, отброшенный из-за переполнения буфера |
| 3 | данные ждут на **другом** канале (необязательный бит; UNETESP 0.3 и новее) |

### Функция 9 - STATUS

При `A` = номер канала возвращает состояние этого канала в DE:

| бит | значение |
|-----|---------|
| 1 (`0x02`) | канал подключён (последнее известное состояние) |
| 2 (`0x04`) | для канала есть принятые, но ещё не отданные данные (необязательный бит: его выставляют только бекенды с `CAP_MULTICHAN`, поэтому сброшенный бит означает «неизвестно», а не «данных нет») |

STATUS читает только память и никогда не обращается к UART, поэтому опрашивать
её между другими делами достаточно дёшево. Если узел закрыл соединение, канал
сообщает бит непрочитанных данных без бита подключения - это признак того, что
читать надо дальше, до `NERR_CLOSED`.

При `A = 0xFF` возвращает состояние сети **без обращения к оборудованию**:
`A = NERR_OK` / `NERR_NONET`, а в DE бит 0 = сеть настроена (переменные среды
опубликованы), бит 1 = `NETINIT` уже выполнен. Удобно для программы запуска,
которой нужно показать состояние без лишних затрат.

### Функция 11 - RESOLVE

Определяет IP-адрес по имени хоста и записывает его в буфер `dest`
вызывающего (не меньше 16 байт) в точечной нотации. На прошивках без
`AT+CIPDOMAIN` (а также в текущем эмуляторе jesperl) возвращает
`NERR_NOTSUP`; этот факт запоминается, поэтому последующие вызовы завершаются
ошибкой сразу. `GETCAPS` при этом всё равно сообщает `RESOLVE`, так как
возможности - неизменное свойство драйвера, а не признак того, что вызов
сработает; проверять нужно то, что функция вернула. Большинству потребителей
RESOLVE вообще не нужен: `CONNECT` принимает имя хоста напрямую и адрес по
нему находит сам ESP.

### Функция 12 - PING

Проверка достижимости в стиле ICMP; DE возвращает время обхода в
миллисекундах.

### Функции 13 / 14 - RXPAUSE / RXRESUME

См. "Как избежать переполнения UART" ниже. Обе возвращают `NERR_STATE` до
`NETINIT`: пока UART не найден, запись в регистр могла бы задеть другую
ISA-карту.

### Функция 15 - GETINFO

Копирует строку со свойством сети в `dest` (завершённую NUL, усечённую до
`max`; `max=0` возвращает `NERR_PARAM`). Поля: 0 тег бекенда ("ESP"), 1 IP,
2 маска, 3 шлюз, 4 MAC, 5 DNS1, 6 DNS2, 7 источник IP ("STATIC"/"DHCP"),
8 SSID, 9 скорость, 10 NTP, 11 часовой пояс, 12 дескриптор оборудования.
Неустановленные поля возвращают пустую строку. В UNETESP значения берутся из
переменных окружения `NET_*`, публикуемых NETUP.

### Функция 16 - LASTERR

Копирует в `dest` **конец** последнего необработанного ответа AT или драйвера:
если ответ длиннее буфера, отбрасывается его начало, а последние байты
сохраняются - именно там находится самое полезное, строка `ERROR` или
`CLOSED`. При `max=0` возвращает `NERR_PARAM`. Это средство диагностики,
аналогичное отладочному хвосту ESP в fido-клиенте binkp.

После неудачного SEND в буфере оказывается

```
send failed <n>: <line>
```

потому что наружу любой сбой транспорта выглядит одинаково - как `NERR_SEND`.
Здесь `n` - внутренний код причины (1 = ESP ответил `ERROR`, 2 = `FAIL`,
3 = таймаут передачи, 4 = ответа не было), а `<line>`, если она есть, - это
последний целиком полученный ответ ESP или строка из проверки связи.
Запоздалое `SEND OK` и перезагрузку модуля проверка определяет так же, как и
раньше, но подробные счётчики байт, захват начала и хвоста ответа,
форматирование LSR и текстовые вердикты в образ DLL намеренно не включены:
`LASTERR` остаётся достаточно информативным, чтобы по нему можно было
действовать, а освободившееся место отдано самому транспорту.

Если соединение отвалилось по таймауту без всяких сообщений, DLL пробует
восстановиться по строгой схеме: до ~10 с опрашивает модуль командой `AT`
через тот же читатель, понимающий `+IPD`; убедившись, что командный режим
жив, один раз повторяет `CIPSTART`; успехом считает либо запоздавшее
`<id>,CONNECT` для нужного соединения, либо `ALREADY CONNECTED` в ответ на
этот повтор. Второй вариант означает, что первая попытка всё-таки открыла то
же самое соединение, но сообщение об этом потерялось. На первой попытке такой
ответ не принимается никогда - там он мог бы относиться к старому, уже
неактуальному соединению. В SEND такая проверка безопасна только после того,
как все данные ушли с компьютера: она может заметить запоздавшее `SEND OK`
или обнаружить перезагрузку модуля, но данные не переотправляет. До появления
приглашения `>` проверять нельзя вовсе - если приглашение просто задержалось,
модуль примет за данные даже команду `AT`, поэтому в этом случае SEND
завершается ошибкой без всякой проверки.

### Функция 17 - SETOPT

- `UNET_OPT_CANCELKEYS` (1): DE=1 включает опрос Esc / Ctrl+Z во время
  блокирующих циклов UART (отменённый приём возвращает `NERR_CANCEL`). По
  умолчанию выключено - DLL никогда не трогает клавиатуру без запроса.
- `UNET_OPT_RXTRIG` (2): DE = 1/4/8/14 задаёт уровень срабатывания
  авто-RTS для RX FIFO 16550. По умолчанию 4. Другое значение стоит
  использовать только для полевой диагностики на конкретном оборудовании (см.
  замечание о переполнении). Возвращает `NERR_STATE` до `NETINIT` (база UART
  ещё не известна).
- `UNET_OPT_SENDSLICE` (3): DE = сколько миллисекунд **тишины** на соединении
  должно пройти, чтобы SEND приостановился с `NERR_AGAIN` вместо того, чтобы
  ждать дальше. При 0 (по умолчанию) отправки остаются полностью блокирующими;
  ненулевые значения меньше 50 поднимаются до 50. Перед использованием
  проверьте бит `UNET_CAP_ASYNCSEND`. См. "Неблокирующий SEND" ниже.

### Неблокирующий SEND (CAP_ASYNCSEND, UNETESP >= 0.4)

`CIPSEND` - это транзакция: как только текст команды ушёл, модуль может
принять вторую его копию за данные, поэтому подход «подождать таймаут и
повторить» здесь небезопасен в принципе. Вместо этого DLL не обрывает начатую
транзакцию, а продолжает её при следующем вызове:

- Если задан `UNET_OPT_SENDSLICE`, то SEND, у которого соединение **молчит**
  целый квант, возвращает `NERR_AGAIN`, а в `DE` - сколько байт подтверждено
  на данный момент. Ничего не переотправляется и ничего не теряется: кадры
  `+IPD`, пришедшие за время паузы, уже отложены для своих каналов.
- Для продолжения нужно повторить **тот же** вызов (тот же канал, буфер,
  длину); ожидание продолжится ровно с того места, где прервалось, - даже
  если на нём оборвался наполовину распознанный префикс `+IPD,` или
  недочитанная строка ответа. Вызов с другим каналом или другими аргументами,
  пока транзакция не завершена, вернёт `NERR_STATE`.
- Между повторами потребитель может обслуживать свой интерфейс, опрашивать
  клавиатуру и свободно вызывать RECV/STATUS: пока отправка приостановлена,
  RECV выдаёт только буферизованные данные и возвращается немедленно (никогда
  не трогая живой поток), а STATUS никогда не обращается к оборудованию.
  `UNET_RXF_XCHAN`/`UNET_ST_RXPEND` при этом работают.
- Функции, отправляющие AT-команды (CONNECT, UDPOPEN, CLOSE, NETDONE, PING,
  RESOLVE, NETINIT), пока SEND не завершён, возвращают `NERR_BUSY` и к UART
  не обращаются. Довести транзакцию до конца может только тот же самый SEND:
  завершись она внутри другого вызова - потерялся бы счётчик отправленных
  байт, а повторный SEND позже продублировал бы данные в потоке. Поэтому SEND
  нужно довести до конца перед CLOSE, NETDONE или выгрузкой DLL; если модуль
  так и не вернулся в командный режим, поможет отдельная утилита `NETRESET`.
- Пока данные идут, квант не срабатывает: он отмеряет именно паузу в обмене,
  а не общую длительность отправки. Зависший ESP просто будет отдавать
  `NERR_AGAIN` раз в квант, пока не оживёт или пока потребитель не прекратит
  попытки.
- Если пауза пришлась на **середину** приёма кадра `+IPD`, работает обычный
  внутренний побайтовый таймаут в 5 с. Уже принятая часть кадра сохраняется,
  счётчик оставшихся байт продолжает действовать, и следующий вызов RECV или
  SEND сначала дочитает этот двоичный кадр и только потом пропустит в UART
  новые AT-команды.

`RACETEST -a` проверяет этот режим от начала до конца (слайс 200 мс, символ
`~` на каждую приостановку, с обычной проверкой непрерывности).

## Поднятие сети

Прежде чем потребитель начнёт пользоваться сетью, её нужно поднять штатными
инструментами, ровно так же, как для самостоятельных утилит:

- **ESP:** запустить `NETUP` (он подключается к Wi-Fi и публикует `NET=WIFI`,
  `NET_ESP_HW`, `NET_ESP_FW`, `NET_ESP_FLOW`, `NET_IP`, `NET_BAUD`, ...).
  `NETINIT` проверяет `NET=="WIFI"` и непустой `NET_ESP_HW`. `NET_ESP_FW`
  равен `2.2.1` или `2.2.2`; потребители, добавляющие путь пассивного приёма
  ESP-AT, должны включать его только при `2.2.2`. `NET_ESP_FLOW` равен `3` или
  `0` и фиксирует режим управления потоком UART, согласованный NETUP; бекенд
  ESP воспроизводит его локально, не переконфигурируя ESP.
- **RTL:** запустить `NETCFG -i` (статически) и/или `IFUP` (DHCP), чтобы были
  опубликованы `NET_IP` и `NET_MAC`.

`STATUS` с `A=0xFF` сообщает это состояние, не обращаясь к карте.

## Сценарии использования

### Запрос / ответ (HTTP GET или POST)

Открыть, отправить весь запрос, читать ответ, пока узел не закроет соединение,
затем закрыть. Работает и для POST с телом любого размера (SEND сам разбивает
на куски):

```
    NETINIT
    CONNECT   chan 0, "example.com", "80"
    SEND      chan 0, request buffer (headers + body), length
loop:
    RECV      chan 0, buf, max, 5000 ms
    ; A=NERR_OK, DE>0 -> обработать DE байт, продолжить цикл
    ; A=NERR_OK, DE=0 -> простой, продолжить цикл или сдаться
    ; A=NERR_CLOSED   -> обработать оставшиеся DE байт, затем остановиться
    CLOSE     chan 0
    NETDONE
```

Гарантия "FIN с последним сегментом" (см. RECV) означает, что последние байты
перед закрытием всегда будут доставлены.

### Интерактивный двунаправленный поток (IRC / telnet / чат)

Та же пара SEND/RECV обслуживает полнодуплексную сессию - никакого особого
"прозрачного" режима не требуется, и одинаковый код работает на обоих
бекендах. Опрашивать следует с коротким таймаутом RECV, чтобы цикл оставался
отзывчивым:

```
    CONNECT   chan 0, host, port
loop:
    RECV      chan 0, buf, max, 150 ms   ; A=NERR_OK/DE=0 означает "пока ничего, но связь жива"
    ; вывести принятые байты; RXPAUSE вокруг медленной работы с экраном/диском (см. ниже)
    ; если пользователь что-то набрал: SEND chan 0, line, len
    ; A=NERR_CLOSED -> сессия завершена
    jr loop
```

**Данные, пришедшие во время SEND.** Кадр от узла может прийти между
приглашением `CIPSEND` и `SEND OK` - на каждую отправку это окно в несколько
десятков миллисекунд. Отправляющая часть ESP разбирает такие вклинившиеся
кадры `+IPD`, не ломая состояние протокола, а **UNETESP сохраняет их
содержимое в отложенном буфере на 2 КБ и отдаёт следующему RECV в порядке
поступления, раньше всех новых данных**, так что байты в этой гонке больше не
теряются. Узел, который отвечает только когда к нему обратились (HTTP, NTP,
большинство протоколов), в это окно вообще не попадает, а по-настоящему
полнодуплексные (чат, telnet-сервер со своей инициативой, binkp) теперь
обслуживаются без потерь и без особых предосторожностей. Замечания:

- Когда RECV опустошил отложенный буфер не до конца, в `IX` остаётся
  выставленным бит 1 - значит, есть ещё сохранённые или недочитанные данные, и
  RECV нужно вызывать дальше, как при обычном чтении в несколько кадров.
- Если очередной вклинившийся кадр не помещается в свободное место буфера, он
  отбрасывается целиком (а не сохраняется частично), и при следующем RECV
  поднимается бит 2 в `IX` - данные потеряны. На практике при одном кадре
  размером с MTU за окно отправки этого не происходит; чтобы так и оставалось,
  **делайте SEND короткими** - одна строка или один пакет за раз.
- **Вычитывать данные перед отправкой** для правильной работы больше не
  обязательно, но в интерактивных циклах, чувствительных к задержкам, привычка
  остаётся полезной.

У бекенда RTL такого окна нет (карта буферизует приём самостоятельно), так что
его потребители ведут себя точно так же. (Сырой прозрачный канал только для
ESP всё ещё можно было бы добавить за зарезервированным битом
`CAP_TRANSPARENT` и слотами 18-23, но переносимый и теперь не теряющий данные
путь - это SEND/RECV.)

### Два канала

Бекенды с `CAP_MULTICHAN` держат два соединения одновременно - канал 0 и канал
1 - что и требуется пассивному FTP: команды и ответы на управляющем
соединении, пока соединение данных передаёт файл. Оба текущих бекенда это
поддерживают (UNETESP - через режим множественных соединений ESP-AT, начиная с
0.3; UNETRTL - начиная с 0.2.5x). Но если появится бекенд с одним каналом, он
этот бит не выставит, поэтому наличие двух каналов нужно проверять по биту
возможностей, а не считать, что они есть всегда:

```
    GETCAPS                            ; DE bit4 (0x0010) = CAP_MULTICHAN
    CONNECT   chan 0, host, "21"       ; управляющее соединение
    ; ... login, TYPE I, PASV -> разобрать ответ 227
    CONNECT   chan 1, pasv_host, pasv_port
    SEND      chan 0, "RETR file",13,10
loop:
    RECV      chan 1, buf, max, 4000 ms   ; данные
    ; A=NERR_OK/DE>0   -> записать DE байт
    ; A=NERR_OK/DE=0   -> пока ничего; выставленный бит3 в IX означает, что данные есть на канале 0
    ; A=NERR_CLOSED    -> сервер закрыл соединение данных: передача завершена
    RECV      chan 0, buf, max, 800 ms    ; заберёт 150/226, когда бы они ни пришли
    CLOSE     chan 1
    ; ... QUIT
    CLOSE     chan 0
    NETDONE                               ; заодно восстанавливает режим одиночного соединения
```

Правила, благодаря которым это работает:

- **Читать каналы по очереди.** Данные обоих каналов идут по одной и той же
  последовательной линии, поэтому блок, пришедший для канала, который сейчас
  *не* читают, откладывается для него, а текущее чтение сразу возвращает
  `DE=0` и выставленный бит 3 в `IX`. Это означает «пора переключиться на
  другой канал», а не «связь простаивает». То же самое показывает `STATUS`
  (`0x04`), причём ничего не вычитывая.
- **Внутри канала порядок сохраняется.** Отложенные данные всегда отдаются
  раньше более новых и раньше, чем `NERR_CLOSED` этого канала.
- **Пока оба канала открыты, работать можно в обе стороны.** Отправка по
  управляющему каналу во время передачи данных - это ровно то, как устроен FTP
  (`REST`, `RETR`, `STOR`, `LIST`); данные, пришедшие во время таких отправок,
  сохраняются так же, как в одноканальном случае выше.
- **Не тянуть с чтением.** У каждого канала свой буфер на 2 КБ. Если канал,
  который сейчас не читают, получит больше этого объёма, лишнее будет
  отброшено, а при его следующем RECV поднимется бит 2 в `IX`. Чтобы буферы не
  переполнялись, читайте каналы попеременно, не затягивайте медленную работу с
  диском и экраном между чтениями и оборачивайте её в `RXPAUSE`.
- **По одному делу за раз.** Не вызывайте `CONNECT`, `RESOLVE` или `PING`,
  пока узел на другом канале может передать что-то по своей инициативе: эти
  функции разбирают построчный AT-ответ и приняли бы данные узла за текст
  ответа. В FTP такого не случается - канал данных открывается между ответом
  `227` и командой передачи.

Загрузка на сервер завершается наоборот: *клиент* закрывает канал данных,
сигнализируя конец файла (`CLOSE` канала 1), а затем читает `226` на
управляющем канале. `CLOSE` дожидается ответа ESP, не проглатывая данные узла,
поэтому `226`, гонящийся с закрытием, не теряется.

## Как избежать переполнения UART (бекенд ESP)

Приём без потерь на скорости зависит от нескольких уровней; потребителю нужно
соблюдать только последний:

1. **Аппаратный RTS/CTS с обеих сторон.** `NETINIT` переводит 16550 в режим
   автоматического управления потоком с порогом срабатывания RX FIFO в 4 байта
   и сообщает ESP `flow=3`. Когда FIFO заполняется, RTS снимается аппаратно, и
   ESP останавливается за время передачи нескольких байт; дальше приём
   притормаживается уже сам собой - через буфер ESP и окно TCP.
2. **Командный режим (+IPD), а не прозрачный.** Границы кадров дают ESP
   безопасные точки для остановки, поэтому пауза в приёме кадр не портит.
3. **RXPAUSE / RXRESUME - забота потребителя.** Перед медленной работой между
   приёмами (запись на диск, перерисовка экрана) вызовите RXPAUSE, а перед
   следующим RECV - RXRESUME. Нужно ли это конкретному бекенду, показывает бит
   `RXFLOW` в `GETCAPS`. Бекенду RTL не нужно: он накапливает данные в самой
   карте, и RXPAUSE у него ничего не делает - поэтому один и тот же код
   потребителя правильно работает с обоими.
4. **RTS управляет кто-то один.** Сама DLL RTS никогда не поднимает - она лишь
   возвращает то состояние паузы, которое задал потребитель. Переключать RTS
   какими-либо другими способами нельзя.

Уровень срабатывания FIFO по умолчанию - 4 байта. Прежняя настройка TR8
оставляла ESP лишь восемь байтовых интервалов, чтобы заметить RTS, и вызывала
периодические переполнения в SpecTalkZX. "Более безопасный" уровень в 1 байт
ограничивает пропускную способность примерно до 1 КБ/с; TR4 оставляет запас в
12 байтовых интервалов и является проверенным значением по умолчанию.
`SETOPT RXTRIG` по-прежнему позволяет выбрать другой уровень для полевой
диагностики.

## Приложение по бекенду RTL (UNETRTL.DLL - руководство по реализации)

Бекенд RTL8019A реализует *те же* номера функций, коды ошибок и семантику
возможностей, поэтому потребитель совместим на уровне исходного кода.
Замечания по реализации для проекта sprinter-rtl8019a:

- **Поднятие сети:** на RTL нет маркера `NET=WIFI`. Сеть следует считать
  поднятой, когда `NET_IP` и `NET_MAC` непусты (публикуются `NETCFG -i` /
  `IFUP`). Рекомендуется также публиковать `NET=RTL` после настройки сети (и
  удалять его при `NETCFG -d`), чтобы лаунчеры могли выбирать DLL по значению
  `NET`; при этом по-прежнему принимать устаревшее состояние (нет `NET=`, но
  установлены `NET_IP`+`NET_MAC`).
- **NETINIT:** опросить карту (учитывая `NET_RTL_HW`) - после этого драйвер
  готов к работе.
- **CONNECT / SEND / RECV / CLOSE:** отображаются на программный стек -
  `RESOLVE.HOST` -> `RESOLVE.NEXT_HOP_FOR` -> `TCP.OPEN`, затем `TCP.SEND` /
  `TCP.RECV` / `TCP.CLOSE`. SEND разбивает на куски по TCP MSS (536); ABI
  скрывает это ровно так же, как UNETESP скрывает предел CIPSEND в 2048.
- **RESOLVE:** программный DNS через `dns_lib` / `resolve_lib`; запись A
  форматируется в точечную нотацию (IPv4). `CAP_RESOLVE` выставлен и работает
  (никакого `NERR_NOTSUP`).
- **PING:** программное ICMP echo (как в `ping.asm` для RTL).
- **UDP:** UDP с фиксированным адресатом поверх встроенного обрамления
  дейтаграмм, используемого утилитами RTL UDPTEST / NTP / TFTP.
- **RXPAUSE / RXRESUME:** пустые операции, возвращающие `NERR_OK`; карта
  буферизует приём в своём кольце на ~14,5 КБ. `CAP_RXFLOW` сброшен.
- **Возможности:** `GETCAPS` сообщает `0x001F` =
  `TCP | UDP | RESOLVE | PING | MULTICHAN`. `CAP_RXFLOW` выключен (пустые
  RXPAUSE/RXRESUME выше); `CAP_RAWETH`/`CAP_LISTEN`/`CAP_ASYNCSEND` не
  выставлены.
- **Два канала (пассивный FTP):** реализованы на обоих бекендах. UNETESP
  делает это через режим множественных соединений ESP-AT (`AT+CIPMUX=1`, по
  одному буферу приёма на канал, `NETDONE` восстанавливает `CIPMUX=0`),
  начиная с 0.3. UNETRTL делает это двумя независимыми контекстами TCP/UDP
  (отдельные кортежи, состояние последовательностей и очередь отложенных
  сегментов на канал вплоть до MSS в 536 байт): по мере того как входящие
  сегменты доходят до головы кольца приёма RTL, они обрабатываются и
  подтверждаются в контексте своего канала, а `UNET_RXF_XCHAN` сигнализирует,
  когда требуется обслужить другой канал. Полные подробности см. в
  `sprinter-rtl8019a/docs/UNETRTL.md` ("Two channels").
